# 캡스톤 부스 체험 시연 설계 문서 (Mongbas)

> **보존용 역사 문서:** 2026-06-05 발표 준비 당시의 설계를 보존한다. 현재 코드·보안 검증 상태의 근거로 인용하지 말고 `README.md`와 비공개 security matrix를 사용한다. 특히 아래의 “강압자도 구분 못 함”, 7/7 연결, 과거 file:line 표는 현재 증거가 아니다.

> **한 줄 요약**: 방문자가 폰으로 직접 투표 → 큰 화면에서 "방금 당신이 던진 그 표"가
> 제공된 게시판 경로와 원장 root가 일치하는지 본인 영수증으로 확인시켜주는,
> 2~3분짜리 **반복 가능한 부스 체험**을 만든다. 느린 부분(네트워크 기동·체인코드 배포)은
> 사전 셋업으로 완전히 분리하고, 발표자는 **관제판 한 화면**만 운전한다.

작성일: 2026-06-04 / 대상 발표: 2026-06-05(금) 캡스톤 전시

## 1. 목표와 제약

### 목표
- **체험 시간**: 방문자 1팀(2~4명)당 **2~3분**, 하루 종일 반복.
- **보안 기능 시연**: 7대 학술 보안 속성과 관련된 기능을 체험하되, 이를 7/7 독립 검증으로 표현하지 않는다.
- **"내 표" 체감**: 추상적 해시 나열이 아니라, *방문자 본인의 영수증*으로
  "제공된 내 표의 포함 경로와 공개 root가 일치한다"를 눈으로 확인시킨다.
- **발표자 편의**: 창을 여러 개 띄우지 않고 **버튼 몇 개짜리 관제판 하나**로 운영.

### 제약 (반드시 지킬 것)
- **선거는 한 번 종료(close)하면 되돌릴 수 없다** → 세션 갈아끼우기 전략 필요(§5).
- **체인코드는 결정론적** → 새 로직 추가 시 `time.Now()`/`rand` 금지 (기존 CLAUDE.md 규칙).
- **체인코드는 단일 파일 유지** (`chaincode/voting/voting.go`).
- **네트워크 기동·체인코드 배포는 5~10분** → 시연 *중*에 절대 하지 않는다(§9 사전 셋업).

### 비목표 (이번 시연에서 안 함)
- 기존 `VoterPage` / `AdminPage` / `VerifyPage` 삭제·대체 안 함 → **심화/백업용으로 유지**.
- 새 백엔드 서버 프로세스 안 만듦 → **기존 Express 확장**.

## 2. 체험 모델 (부스 운영 방식)

무대 발표가 아니라 **부스 체험**이다.

- 방문자가 부스에 오면 **우리(팀)가 직접 체험을 시켜준다.**
- **방문자**: 폰으로 후보 선택 → 투표 (가장 쉬운 부분만 직접 → 참여감).
- **우리(발표자)**: 노트북에서 **관제판 + 큰 화면 검증**을 운전.
- 핵심 무기: "방금 **당신이** 던진 표가 블록체인에 **이렇게** 들어갔고,
  누가 건드리면 **이렇게** 들통난다"를 **그 자리에서 그 사람 영수증으로** 보여주는 것.

### 장비/동선
```
   [관객 폰들] --QR스캔--> 폰용 /kiosk (투표만)
                                 │
                                 ▼  (tailnet-only HTTPS → loopback :3000)
   [부스 노트북] ── 큰 화면 ──> /control (관제판) + 내 표 추적 검증화면
        └ 백엔드 Express(:3000) + 빌드된 프론트엔드 서빙 + Fabric 네트워크
```
- 노트북 화면을 모니터/빔으로 미러링하면 구경하는 사람도 같이 본다(crowds attract crowds).
- 기다리는 사람용: 옆에 1분 설명 포스터 또는 루프 영상 1개(선택).

## 3. 체험 흐름 (방문자 1팀 시나리오)

| 단계 | 행동 (누가) | 화면 | 드러나는 보안 속성 |
|---|---|---|---|
| ① 맞이 | (발표자) 관제판 **[새 세션 시작]** → 깨끗한 선거 준비 + QR 갱신 | 관제판 | — |
| ② 투표 | (방문자) 폰 QR 스캔 → 후보 선택 → **투표** | /kiosk | **암호화 투표** (공개 원장에는 선택 평문을 기록하지 않음; 전체 익명성은 별도 미검증) |
| | → 폰에 **큰 영수증**: `추적번호 7F3A-90BC-1234` | /kiosk 완료 | 일회용 admission 경로(eligibility 증거 아님) |
| | → 큰 화면 라이브 카운터 1,2,3… 올라감 | 관제판 | — |
| ③ 종료 | (발표자) **[집계 종료 & 결과]** | 관제판 | **Fairness** (종료 전 중간집계 불가) |
| | → 후보별 막대그래프 결과 표시 | 관제판 | — |
| ④ **내 표 검증** ★ | (발표자) 방문자 영수번호 `7F3A-90BC-1234` 입력 | 내 표 추적 | |
| | → 게시판 좌라락 흐르다 **내 줄에서 멈춰 노랗게 점등** | | **Recorded-as-Cast** |
| | → Merkle 경로 위로 점등 → **봉인(root) 일치 ✓** | | (개별 검증성) |
| | → "당신 표는 최종 N표 중 1표" 막대에 톡 쌓임 | | **Universal Verifiability** |
| ⑤ 변조 데모 | (발표자) 번호 한 글자 바꿔 재검증 → **빨간 X, 봉인 깨짐** | 내 표 추적 | 무결성 / 변조 탐지 |
| ⑥ **공개 화면의 평문 선택 제한** | (발표자/방문자) 관리자 UI가 암호문·해시 중심으로 표시됨을 확인 | 관리자 시점 패널 | **제한된 UI 관찰 증거** (root·trustee·issuer 공모에 대한 전체 ballot secrecy/익명성 증거는 아님) |
| ⑦ 불투명 API 데모 (선택) | normal/panic proof가 둘 다 유효하고 고정 길이임을 표시 | API transcript mitigation | **전체 Coercion Resistance 증명 아님** |
| → 반복 | 다음 팀 오면 ①부터 ([새 세션] 한 번이면 리셋) | | |

> Cast-as-Intended(Benaloh 챌린지), ZKP 수식 검증 등 **심화 내용은 "심화 탭"으로 분리**하여
> 질문하는 심사위원에게만 보여준다. 메인 체험 2~3분에는 넣지 않는다.

## 4. 시스템 구성 (아키텍처)

### 새로 만들지 않는 것
- 백엔드 Express 서버 (이미 모든 API 보유 — §8 참조)
- Fabric 네트워크 / 체인코드 (그대로)
- 기존 3개 페이지 (`VoterPage`, `AdminPage`, `VerifyPage`) — 유지

### 추가/변경하는 것
| 층 | 항목 | 내용 |
|---|---|---|
| 프론트엔드 | `pages/KioskPage.jsx` | 폰용 초경량 투표 (§6.1) |
| 프론트엔드 | `pages/ControlPage.jsx` | 발표자 관제판 (§6.2) |
| 프론트엔드 | 내 표 추적 검증화면 | `VerifyPage`의 Merkle 모드를 개선하거나 별도 컴포넌트 (§6.3) |
| 프론트엔드 | 라우팅 | `App.jsx`/`main.jsx`에 **URL 쿼리 감지** 추가 (아래) |
| 프론트엔드 | 의존성 | `qrcode` (관제판 QR 생성) 추가 |
| 백엔드 | 정적 서빙 | 빌드된 프론트엔드를 Express가 서빙 (`express.static`) |
| 백엔드 | (선택) 엔드포인트 | 라이브 표 수 등 경량 추가 (§8) |
| 인프라 | Tailscale Serve | loopback :3000 → tailnet-only HTTPS → QR |

### 라우팅 방식 (react-router 미설치 → 가볍게)
현재 `App.jsx`는 `tab` state로 페이지를 전환한다. URL 진입(QR)을 위해 **쿼리 파라미터를 감지**해
탭 UI(헤더) 없이 단독 페이지를 렌더한다:

```jsx
// main.jsx 또는 App.jsx 최상단
const params = new URLSearchParams(window.location.search);
const appMode = params.get('app');           // 'kiosk' | 'control' | null
const electionId = params.get('e');           // QR에 박힌 선거 ID

if (appMode === 'kiosk')   return <KioskPage electionId={electionId} />;
if (appMode === 'control') return <ControlPage />;
// 그 외에는 기존 탭 UI(App) 그대로
```
- 폰 QR: `https://<ngrok>/?app=kiosk&e=<electionID>`
- 관제판: 노트북에서 `http://localhost:3000/?app=control` (또는 ngrok URL)
- react-router를 굳이 추가하지 않아 빌드/복잡도 최소화. (원하면 나중에 교체 가능)

### 단일 오리진 권장
빌드된 프론트엔드를 **백엔드(:3000)가 직접 서빙**하면 폰·API가 same-origin → CORS 불필요,
**tailnet-only HTTPS reverse proxy 1개**로 끝. 실제 원격 실증은 backend-served production build를 사용한다.

## 5. 세션 갈아끼우기 메커니즘

### 왜 필요한가
- 집계·검증을 보여주려면 선거를 **종료(close)** 해야 하는데, **종료하면 되돌릴 수 없다.**
  - 선거 1개만 쓰면: 한 팀 끝내고 종료 → 다음 팀이 투표 불가.
  - 한 선거를 안 닫고 계속 쓰면: 모든 팀 표가 섞이고, "종료→집계→검증"을 **한 번**만 보여줌.
- → **팀마다 새 선거**를 만들어 매번 깨끗한 "투표→종료→집계→검증" 전체 사이클 제공.

### 어떻게 (관제판 [새 세션 시작] 버튼 = 원클릭 체이닝)
```
[새 세션 시작] 누름:
  1) electionID 생성 (클라이언트: 예) "DEMO_" + localStorage 카운터++  → 매번 유일)
  2) POST /api/elections            (생성, 후보 프리셋, EncryptionMode=elgamal)
  3) POST /api/elections/:id/activate (활성화)
  4) 현재 세션 = 이 ID 로 갱신, QR 즉시 재생성 (?app=kiosk&e=DEMO_n)
  5) 라이브 카운터 0부터 폴링 시작
```
```
[집계 종료 & 결과] 누름:
  1) POST /api/elections/:id/close
  2) POST /api/elections/:id/merkle        (Merkle 트리 구축 → 개별 검증 준비)
  3) POST /api/elections/:id/publish-audit  (게시판 공개 → 누구나 검증)
  4) GET  /api/elections/:id/tally          (결과 막대그래프)
  → 이후 §6.3 내 표 추적 검증 가능
```
- 발표자는 이 **두 버튼 사이만 오가면 됨**. 창 이동 없음.
- 원장에는 선거가 계속 쌓이지만, 시연 규모(팀당 수 표)에선 성능 문제 없음.
  보존할 증거를 내보내고 원장 폐기를 승인한 경우에만 `network.sh clean --confirm-destroy-ledger`로 정리.

### 자유로운 열고/닫기 + 투표 자동 주입 (요청 반영)
- **세밀 제어**: 원클릭 버튼과 **별개로** `생성` / `활성화` / `종료` 개별 버튼도 둬서
  발표자가 선거를 자유롭게 열고 닫을 수 있게 한다.
- **투표 N개 자동 주입**: 관제판 `[투표 N개 자동 생성]` 버튼.
  - 백엔드 신규 엔드포인트 **`POST /api/elections/:id/seed-votes { count, randomize }`**:
    서버에서 N명분(voterSecret 생성 → nullifier 계산 → ElGamal 암호화 + 유효성 ZKP →
    체인코드 `CastVote`)을 한 번에 처리. `full-election-e2e.js`의 투표 로직 재사용.
  - 폰 실투표 몇 개 + 자동 투표로 게시판·집계를 풍성하게(데모 설득력 ↑).
  - ⚠️ 결정론 제약 유지: voterSecret/난수는 **백엔드(앱 레이어)에서** 생성해 체인코드엔
    이미 만들어진 암호문만 전달 (체인코드 내 `rand` 금지 규칙 불변).

### 대안 (운영이 더 단순하길 원하면)
- **하루 한 선거 + 라이브 카운터**: 종일 한 선거를 열어두고 카운터만 키우다가,
  정해진 시연 타임에만 한 번 극적으로 종료·집계. 팀별 깨끗한 사이클은 포기.
  → 기본은 "세션 갈아끼우기" 권장, 운영 부담 크면 이 대안으로 전환.

## 6. 화면 설계

### 6.1 `/kiosk` — 폰용 초경량 투표

**목표**: 설명 없이 30초 안에 끝. 후보 고르고 버튼 누르면 큰 영수증.

- **숨기는 것**: 인증/선거선택(자동), Blind/ElGamal 토글(기본 ON 고정), Benaloh(심화로 이동),
  voterSecret 입력(자동 생성).
- **자동 처리**:
  - QR의 `?e=` 로 선거 자동 선택, `GET /api/elections/:id` 로 후보 로드.
  - 자격증명 자동 발급: `POST /api/credential/idemix` (데모용 공용 enrollment 또는 풀).
  - `voterSecret` 클라이언트 생성 → localStorage 저장.
  - `nullifier = SHA256(voterSecret + electionID + blindingFactor)` 계산
    (blindingFactor는 `GET /api/elections/:id/blinding-factor`).
  - ElGamal 암호화 + 유효성 ZKP 생성 → `POST /api/vote`.
- **화면**:
  ```
  ┌─────────────────────┐
  │   2026 모의 대선       │
  │  ◯ 기호1 Alice        │
  │  ◯ 기호2 Bob          │
  │  ◯ 기호3 Charlie      │
  │   [   투표하기   ]     │
  └─────────────────────┘
        ▼ 투표 후
  ┌─────────────────────┐
  │      ✅ 투표 완료       │
  │  내 추적번호           │
  │   ┌───────────┐       │
  │   │7F3A-90BC-1234│     │  ← 크게! (48-bit 표시 prefix)
  │   └───────────┘       │
  │  "이 번호를 기억하세요.  │
  │   검증할 때 씁니다"     │
  │   [QR]  (전체 nullifier)│
  └─────────────────────┘
  ```
- **영수번호 설계**: 화면 표시 코드는 `nullifier` 앞 12 hex (`7F3A90BC1234` → `7F3A-90BC-1234`).
  검증 시 게시판에서 prefix를 찾되, 둘 이상 일치하면 더 긴 값을 요구하고 단일 일치를 가정하지 않는다.
  전체 nullifier는 QR로도 제공(정확 매칭/스캔용).
- **심화 토글**(작게): Benaloh 챌린지, 패닉 자격증명 → 관심자에게만.

### 6.2 `/control` — 발표자 관제판

```
┌──────────────────────────────────────────────┐
│  현재 세션: DEMO_007      상태: ● 진행중          │
│  실시간 투표 수:  12표      (2초마다 갱신)         │
│  ┌── QR ──┐   "여기 찍고 투표하세요"               │
│  │ ▓▓▓▓▓ │   https://xxxx.ngrok.../?app=kiosk… │
│  └────────┘                                      │
├──────────────────────────────────────────────┤
│ [ 새 세션 시작 ]     ← 생성+활성화+QR갱신 원클릭     │
│ [ 집계 종료 & 결과 ] ← close+merkle+publish+tally  │
│ [ 내 표 검증 열기 ]  ← 검증화면으로                 │
│ 세밀제어: [생성] [활성화] [종료]                    │
│ 자동주입: [투표 +5] [투표 +10]  (seed-votes)        │
├──────────────────────────────────────────────┤
│  결과 (종료 후):                                  │
│   Alice  ████████  6                             │
│   Bob    █████     4                             │
│   Charlie██        2                             │
└──────────────────────────────────────────────┘
```
- 라이브 카운터: `GET /api/elections/:id` 폴링(2초) → `totalVotes` 표시(추가 엔드포인트 불필요).
- QR: `qrcode` 패키지로 클라이언트 생성. 세션 바뀌면 자동 갱신.
- 후보 프리셋: 코드에 기본 후보 배열 상수(예: Alice/Bob/Charlie) → 매번 동일.
- 세밀 제어 + 자동 주입 버튼은 §5 "자유로운 열고/닫기" 반영.

### 6.2-b 관리자 시점 패널 — 공개 화면 관찰 범위 (양방향 체험)

체험을 **투표자 방향 / 관리자 방향 두 갈래**로 진행:
- **투표자 체험**: 폰으로 투표 → 내 표 추적(§6.3) — "내 표가 확실히 들어갔다".
- **관리자 체험**: 관리자 UI에서 공개 원장에 선택 평문이 나타나지 않는 제한된 관찰을 시연한다.
  이는 issuer, trustee, peer DB, backend 또는 root 운영자 공모에 대한 프라이버시 증거가 아니다.

**패널이 보여주는 것 (해당 표 1건의 원장 실제 상태):**
```
관리자가 볼 수 있는 전부:
  nullifierHash : 9f3a...e1   ← 공개 표식 (선거 내 재사용·재투표 연결 가능)
  encryptedBallot: (g^r, g^m·y^r) = 0x8c2f...   ← 암호문
  ZKP          : 유효성 증명 ✓ (내용은 안 드러남)
  ───────────────────────────────────
  후보?  ❌ 불가      이름?  ❌ 불가
  이유:
   1) 현재 ElGamal 정상 집계 경로는 암호문을 결합해 합계를 복호화함
   2) 합계 복호화도 2-of-3 기관 키조각(Shamir) 모여야 가능 — 관리자 혼자 불가
   3) 신원은 PDC에만, orderer엔 안 감 / 공개 식별자는 단방향 해시
```
- ⚠️ **반드시 ElGamal 모드 전제**: AES 레거시 모드는 게시판 검증 시 개별 표를 복호화하므로
  프라이버시 주장이 깨진다. seed-votes·새 세션 모두 `EncryptionMode=elgamal` 고정.
- 데이터 출처: `GET /api/elections/:id/bulletin-board` (암호문·해시·ZKP는 이미 공개 데이터).
- 구현 전 확인 사항: "개별 복호화 경로가 코드에 없고 합계만 복원"이 실제로 그런지
  `chaincode/voting/voting.go` 의 tally 경로 1회 검증(README상 BSGS 합계 복원이 맞음).

### 6.3 내 표 추적 검증화면 ★ (핵심)

**기존 `VerifyPage` Merkle 모드를 "스토리텔링" 버전으로 개선** (또는 별도 컴포넌트).
실제 검증형 투표(Selene)의 통찰 차용: *추적번호가 결과 속 내 표를 가리킨다.*
데모에서 평문 후보를 보여주는 화면은 학습용 UI일 뿐이며 **receipt-freeness 또는 coercion resistance와 양립한다는 증거가 아니다**.
실제 증거 화면과 분리하고 이 경계는 §7 주석과 함께 표시한다.

**4단계 애니메이션** (영수번호 하나로 전부 연결):
1. **영수증 등장**: "당신의 추적번호 **7F3A-90BC-1234**" — 공개 게시판에서 포함 후보를 찾는 표시 prefix이며 비밀 자격증명이 아니다.
2. **게시판에서 내 줄 찾기**: 전체 게시판이 흐르다 **내 줄에서 멈추고 노랗게 점등**
   + "↑ 바로 이 줄이 당신의 표". (게시판 = `GET /api/elections/:id/bulletin-board`)
3. **Merkle 경로 점등**: 내 leaf → 형제 노드와 합쳐지며 **위로 한 칸씩 빛나 root 도달**
   → "내가 계산한 봉인 = 블록체인 봉인 ✓". (`GET /api/elections/:id/proof/:nullifier`,
   기존 `MerkleTreeDiagram`/`computeMerkleRootFromProof` 재사용)
4. **집계 기여**: "당신의 표는 최종 **N표 중 1표**" → 막대그래프에 **내 1표가 톡 쌓이는** 연출.

**용어 한글화** (해시 원문은 작게 부가표시):
| 기존(전문용어) | 체험용 표현 |
|---|---|
| nullifierHash | **내 표 추적번호** (영수증 번호) |
| Merkle Leaf Hash | **내 표의 지문** |
| Root Hash (on-chain) | **전체 투표함의 봉인** |
| "계산한 Root = 블록체인 Root" | **"제공된 내 표와 경로로 공개 봉인을 다시 계산할 수 있음"** |

**변조 실패 데모** (§3 ⑤, 가장 강렬):
- 영수번호/후보를 한 글자 바꿔 재검증 → root 불일치 → **빨간 X + 봉인 깨짐 애니메이션**
  → "이 입력 변경은 포함 검증에서 탐지됩니다."

**강압 비교** (§3 ⑥, 기존 `DeniableDiagram` 재사용):
- normal/panic proof를 **좌우로 나란히** 검증 → 둘 다 유효. 발표에서는 “API body/timing 분류 공격을 보완했지만 기관 공모·재투표 패턴을 포함한 전체 강압 저항성은 미검증”이라고 설명.

## 7. 7대 보안 속성 ↔ 체험 매핑

| 속성 | 메커니즘 | 체험에서 보이는 지점 |
|---|---|---|
| Ballot Secrecy(비밀투표) | Exponential ElGamal | ② 폰 투표 시 서버는 암호문만 — "평문 안 보냄" |
| Cast-as-Intended | Benaloh 챌린지 | (심화 탭) 준비→감사로 암호화가 의도대로임 확인 |
| Recorded-as-Cast | Merkle 증명 | ④ 게시판 내 줄 점등 + 봉인 일치 |
| Tallied-as-Recorded | Chaum-Pedersen ZKP | ④ 집계 기여 / (심화) ZKP 검증 |
| Universal Verifiability | 게시판 + ZKP | ④ 게시판 공개 — 누구나 검증, ⑤ 변조 탐지 |
| Eligibility Verifiability | HMAC/Ed25519 자격증명 | ② 폰 접속 시 자동 발급(로그) |
| Coercion Resistance(목표) | opaque proof API/panic/revote prototype | ⑥에서 API 보완만 시연; 속성 전체는 `unverified` |

> **Receipt-freeness 경계 주석**: 실제 시스템에서 검증화면은 후보 평문을 노출하지 않는다
> (강압자에게 증거가 됨). **데모에서는** 방문자 본인이 방금 찍었고 강압 상황이 아니므로
> 이해를 돕기 위해 평문을 보여준다. 발표 시 "실제 운영에서는 ⑥처럼 영수증으로 후보를
> 증명할 수 없게 막는다"고 1줄 설명 → 모순 아님을 분명히 한다.

  백엔드 변경 불필요.

## 9. 사전 셋업 절차 (느린 부분 분리)

**발표 전날/당일 아침에 1회** (시연 중 절대 안 함):
```bash
# 1) 네트워크 기동 + 체인코드 배포 (5~10분, 가장 느림)
cd mongbas/network
./scripts/network.sh up
./scripts/network.sh deploy

# 2) 프론트엔드 빌드 (정적 서빙용)
cd ../frontend
npm run build           # dist/ 생성

# 3) 백엔드 기동 (rate limit 유지 + 정적 서빙)
cd ../application
npm start    # :3000, dist/도 서빙

# 4) tailnet-only HTTPS (QR용) — 계정 Serve 활성화 후에만
tailscale serve --bg http://127.0.0.1:3000
#   → https://xxxx.trycloudflare.com/?app=kiosk&e=... 를 QR로
#   대안: ngrok http 3000 (무료는 첫 방문 경고 페이지 있음)
#   백업: 같은 WiFi면 CORS_ORIGIN에 노트북 LAN IP 추가 후 http://192.168.x.x:3000
```
- **시연 중 하는 일**: 관제판 [새 세션] / [종료 & 결과] / 내 표 검증. 끝.

### 서버 호스팅 정리 (유료 불필요 / DB 불필요)
| 구성요소 | 정체 | Docker | 위치 | 비용 |
|---|---|---|---|---|
| Fabric 네트워크 | peer/orderer/CA/CouchDB | ✅ 필요 | 부스 노트북 | 무료 |
| 백엔드 Express(:3000) | Node.js API | ❌ | 부스 노트북 | 무료 |
| 프론트엔드 | 정적(dist) | ❌ | 백엔드가 서빙 | 무료 |
| private HTTPS | Tailscale Serve | tailnet 구성 필요 | — | 계정 정책에 따름 |

- **유료 클라우드 서버 불필요** — 전부 부스 노트북에서 구동. Docker는 *블록체인 네트워크에만*
  필요(기존과 동일). 폰은 승인된 tailnet의 Tailscale Serve 주소로만 접속한다.
- **별도 DB 불필요**: 모든 상태(선거·표·집계·게시판·Merkle)는 **블록체인 원장(=상태 저장소)**
  에 저장된다. Fabric 내부적으로 **CouchDB 컨테이너**가 상태 DB로 이미 떠 있고(네트워크에 포함),
  이게 곧 DB 역할. 우리가 PostgreSQL/Mongo 같은 외부 DB를 따로 붙일 필요는 없다.
  - 백엔드의 세션/voter 레지스트리는 인메모리 수준이라 데모엔 충분.
  - 단, 백엔드를 재시작하면 인메모리 상태(세션 등)는 날아가므로, 선거 데이터처럼 보존이
    필요한 건 전부 원장에 있으니 안전. (자세한 한계는 §12-아래 "DB/상태" 참조)

## 12. 결정 완료 / 남은 결정

### 결정 완료
- 기존 프론트엔드 유지 + 새 페이지 추가 (전체 파이프라인 뷰 보존).
- 세션 갈아끼우기 방식 채택 + 자유로운 열고/닫기 + 투표 자동 주입.
- 부스 1인 체험, 노트북에서 서버·관제·집계·검증 모두 구동.
- 체험 양방향(투표자 / 관리자) — 관리자 시점 패널에서는 공개 UI의 암호문 표시 범위만 시연.
- 서버: Linux loopback backend + tailnet 내부 Tailscale Serve. Funnel·공개 터널은 별도 승인 없이는 사용하지 않음.

### 남은 결정 (기본값으로 진행 가능)
1. **자격증명 발급 방식**: 데모용 공용 enrollment 1개 vs 사전 시드한 풀(voter1..N).
2. **내 표 추적**: `VerifyPage` Merkle 모드 개선 vs 별도 신규 컴포넌트.
3. **후보 프리셋**: 고정(Alice/Bob/Charlie) vs 한글 후보명.
4. **심화 탭 범위**: Benaloh / ZKP 수식 / Shamir 중 어디까지.

## 13. 비판적 분석 — 이 방향에서 추가로 필요한 기능

> 프로젝트를 부스 체험 관점에서 비판적으로 본 "빈틈". 우선순위 표시.

**[필수에 가까움]**
- **B-1. 동형 집계 "개별 미복호화" 코드 검증**: 프라이버시 주장(§6.2-b)의 근거.
  `voting.go` tally 경로에서 개별 복호화가 정말 없는지 확인 — 없으면 데모 주장이 거짓이 됨.
- **B-2. 키오스크 동시성**: 여러 폰이 같은 세션에 동시 투표 시 nullifier 충돌/세션 꼬임 점검.
  voterSecret이 폰마다 달라 충돌은 없어야 하나, 자격증명 공용 시 동시 발급 경합 확인.
- **B-3. 재투표(last-vote-wins) 시각화**: 강압 데모에서 "패닉 후 진짜표로 덮어쓰기"가 핵심인데,

- **B-4. 관리자 시점 "복호화 시도 실패" 연출**: 관리자가 암호문 복호화를 눌러보면

### 14-2. 문제별 해결 (적용/계획)

**🟢 즉시 해결 완료 (재배포 불필요, 문법검사 통과)**
- **단일 표 Merkle 버그**: `crypto.js computeMerkleRootFromProof`가 빈 proof일 때
  `SHA256(leaf)` 반환하도록 수정 → 체인코드와 일치. (프론트 전용, 적용 완료)
- **키오스크 자격증명 다수 폰**: `credential.js`에 데모 풀 `demo001..demo100` + 공용 `demo`
  추가(비운영 한정). 폰마다 고유 ID 배정 가능, 표 구분은 nullifier가 담당. (적용 완료)

**🟡 구현 단계에서 해결 (P0/P1 작업에 포함, 안전·재배포 불필요)**
- **진행중 표수(라이브 카운터)**: 체인코드 변경 없이 **백엔드 인메모리 카운터**로 해결.
  `POST /api/vote` 성공 & `evictCount===0`일 때 `count[electionID]++`,
  선거 생성 시 0 리셋, `GET /api/elections/:id/live-count` 신설. (seed-votes도 같은 경로라 자동 반영)
- **정적 서빙 + 라우팅 + QR**: `app.js`에 `express.static(dist)` + SPA catch-all 추가,
  `App.jsx`에 `?app=kiosk|control` 쿼리 감지, `qrcode` 의존성 추가.
- **기본 ElGamal**: `/control`의 [새 세션]이 항상 `encryptionMode:'elgamal'` 전송.
- **"내 줄 하이라이트" UI**: 게시판 데이터에 `nullifierHash` 이미 존재 → VerifyPage에
  목록 렌더 + 영수번호(기본 12 hex prefix, 충돌 시 연장) 매칭 하이라이트 추가.
- **seed-votes**: 신규 엔드포인트가 데모 자격증명 발급→ElGamal 암호화+ZKP→CastVote
  (e2e 로직 재사용). 공개 터널에서는 rate limit을 유지하므로 대량 주입은 별도 loopback 평가 profile에서만 수행한다.
- **불투명 API 데모 전제**: 현재 브라우저는 256-bit verification receipt에서 `normalLookupToken`/`panicLookupToken`을 파생한다. 과거 `normalPWHash`/`panicPWHash` 경로는 사용하지 않는다.

**🔴 발표 정직성 직결 — 결정 필요 (코드/내러티브 선택)**
- **P-1. Shamir 2-of-3 ↔ ElGamal 집계키**: 현재 ElGamal 모드에선 단일 관리자가 *합계*를
  복호화 가능(개별 표는 여전히 불가 — 이건 사실). 두 갈래:
  - (A) **내러티브 정정(권장, 무위험)**: 프라이버시 데모는 "현재 정상 tally 경로는 암호문을 집계해 합계만 복호화한다"로 한정한다. 2-of-3은 *원장 기록 합의(endorsement)* + Shamir는 *AES 키 보관*
    기능으로 설명. B-4 연출은 "키 조각 부족"이 아니라 **"개별 복호화 함수 자체가 없음"** 으로 재구성.
  - (B) **코드 보강(고난도, 위험)**: 체인코드에서 ElGamal 개인키도 Shamir 분할/임계복원하도록
    수정 → "단독 복호화 불가" 주장이 ElGamal에서도 참. 발표 전 재배포·테스트 리스크.
- **P-2. 클라이언트 ZKP 검증(V3)**: "당신 브라우저가 직접 수학 검증"은 사실이 아님(체인코드가 검증).
  - (A) **내러티브 정정(권장)**: "누구나 공개 게시판 데이터로 *비밀키 없이* 재검증 가능
    (universal verifiability)"로 표현 — 이건 사실(verify-public).
  - (B) `crypto.js:392 verifyChaumPedersen`를 게시판 검증 경로에 실제 연결(추가 작업).
